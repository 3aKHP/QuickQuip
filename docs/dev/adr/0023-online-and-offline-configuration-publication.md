# ADR-0023：通过不可变快照完成在线与停服发布

- 记录日期：2026-10-26
- 原始决策日期：2026-10-26
- 替代：[ADR-0001](0001-config-snapshot-publication.md)

## 背景

在 [ADR-0001](0001-config-snapshot-publication.md) 的设计中，配置发布依赖运行中的 Bot 进程领取跨进程控制任务来生成并确认新快照。但在配置同步与版本部署场景下，部署流程既不能擅自拉起原本处于停止状态的服务，也需要在 Bot 暂停期间直接安装新配置并推进“已发布版本”指针；尤其当 LLM 配置与人格文件、客户端 Profile 模板同批更新时，下一次启动必须直接读取与新磁盘资产配套的目标配置快照，否则启动校验便会因旧快照引用已删除或改名的资产而失败。

## 决定

在保留“编辑草稿、不可变快照、已发布版本、Bot 实际加载版本”四层分离模型的基础上，同时支持在线任务发布与停服直接发布两种路径：

- **存储分工**：配置正文与本环境修订历史保存在配置库（`config/managed/config.db`），跨进程控制任务、已发布版本指针与 Bot 运行心跳保存在运行库（`data/config_runtime.db`）；认证字段继续仅存储根 `.env` 的变量引用并在运行期展开。
- **在线发布路径**：Bot 在线时，Web Admin 的“应用配置”操作继续创建绑定不可变快照的控制任务，由 Bot 进程领取任务、加载新快照并回报实际加载版本。
- **停服发布路径**：配置部署服务新增停服发布入口。调用方必须同时持有目标 Bot 的生命周期独占锁与配置写入锁，在完成配置文档、磁盘资产、环境变量及作用域引用的完整校验后，将不可变快照写入存储，并在同一个运行库事务内记录停服发布结果、更新已发布版本指针（若运行库中仍存在未收尾的独立在线应用任务则拒绝并返回冲突）。停服发布保留上一次实际加载的修订号记录，同时清空旧 Bot 实例的运行租约与心跳，使后台界面能够清晰区分“配置已发布”与“等待下次启动加载”。若部署前服务原本处于停止状态，发布完成后继续保持停止，待下次启动时直接加载新发布快照。
- **草稿隔离与修订号单调递增**：部署写入的目标快照与后台编辑草稿分开存放，允许目标环境保留尚未发布的独立草稿；修订号在草稿、发布快照与历史记录之间全局单调递增分配，后续草稿编辑不会重用部署快照占用的编号，内容未发生变化的重复保存则保持原修订号不变。
- **原生与容器进程托管**：源码与 Windows 懒人包使用项目自带的轻量启动器父进程托管 Bot 与 Web 子进程——父进程驻留原终端与标准输出流，响应私有控制文件的暂停与恢复请求；子进程在运行期持有生命周期独占锁，并在正常退出时主动释放。容器环境则由 Docker Compose 控制启停。停服发布完成并释放独占锁后，部署流程仅恢复操作前原本正在运行的服务。

## 方案与理由

如果在 Bot 停止时跳过快照发布、把发布推迟到下次启动，远端配置回流（`pull`）在停服窗口内就会一直读到过期的旧发布版；一旦同批替换了磁盘上的人格或 Profile 模板，旧快照还会在下次启动初期引发引用失配。引入停服发布入口可以在文件安装阶段一次性对齐配置快照与磁盘资产，把“配置已正式成为当前发布版”与“进程是否已启动加载”交由发布指针和运行心跳分别准确表达。

以操作系统的文件与进程级生命周期独占锁作为 Bot 已停止的客观凭据，比单纯依赖命令行传入 `--offline` 标志或检查可能过期的历史心跳更可靠；由轻量父进程保有子进程控制权，则解决了源码直跑模式下外部同步脚本暂停服务后无法在原终端恢复子进程的难题。

## 影响

部署事务统一负责受管文件、配置库以及当次发布指针的回滚恢复，不触碰聊天归档、会话记录等业务运行数据。既有源码安装与 Windows 懒人包在升级接入受管启停能力时，需切换至新版启动入口。

实现与回归测试需重点覆盖生命周期独占锁互斥校验、线上独立未发布草稿与修订历史保留、目标环境全量引用预检、旧磁盘资产替换后启动兼容性、Windows 与 Linux 原生启停托管以及后台加载状态展示。
