# QuickQuip 版本号约定

本项目采用三段式版本号 `Major.Minor.Patch`，参考 SemVer 的格式，并借鉴 Minecraft 的主题更新与系列内累积更新习惯。版本号用于表达产品阶段、更新主题和迭代归属；兼容性与升级要求以各版本发布说明为准。

本文是非强制性的发布决策参考，自采用之日起适用。维护者可以根据实际需要作出例外，并在必要时说明原因。历史版本保留原有编号与发布记录，不追溯调整。分支、验证、评审与发布操作见 [`branching.md`](branching.md)。

## 正式版本

| 位置 | 含义 | 选择原则 |
|---|---|---|
| Major | 产品大阶段 | 保持开放；体系架构、技术栈或产品定位发生重大变化时，由维护者综合考虑是否提升。 |
| Minor | 主题更新 | 围绕一个值得独立介绍的主题形成新系列，可以涉及新功能、体验、基础设施或架构治理；允许存在不兼容变化。 |
| Patch | 主题更新内的累积更新 | 延续当前系列，容纳修复、优化、功能补全、小型能力扩展、内部重构和部署加固，以保持向后兼容为默认目标。 |

主题允许有一定宽度，同次发布可以包含其他配套改动。代码量、Commit 类型和 PR 数量仅供参考，版本选择由发布内容与主题归属决定。出现值得独立命名和介绍的新方向时，优先考虑开启下一个 Minor。

“累积”表示包含同一系列此前版本的更新内容。能否跨多个版本直接升级、是否需要中间迁移，以升级说明为准。发布可以按一批工作完成的节奏进行，无需固定周期。

正式版本保持递增，提升 Minor 或 Major 时将右侧各段归零。可以为纪念或系列收尾选择特定的 Patch 号并跳号。纪念编号与“稳定收尾”等表述不自动构成长期支持承诺；推荐部署版本、维护期限和修复范围另行说明。

## 兼容性与升级说明

同一 Minor 系列以兼容升级为默认目标。因缺陷修复、安全加固或外部依赖变化确需调整既有行为时，Patch 可以例外；应控制影响范围，并说明原因与处理方法。Minor 允许不兼容变化，也可以完全兼容。

评估升级影响时，关注群聊与私聊命令、配置字段与默认行为、管理 API、部署环境与启动方式，以及持久化数据和迁移行为。

涉及以下情况时，在 CHANGELOG 对应版本开头列出“升级说明”：

- 需要手动修改配置、部署脚本或运行环境。
- 命令、API 或默认行为发生影响既有使用方式的变化。
- 存在数据迁移、升级顺序要求或回退限制。

升级说明写明受影响的版本或使用场景、变化内容和所需操作。自动迁移且无需操作的情况也应简要注明；已知回退限制单独说明。版本号不构成严格的 SemVer 兼容性承诺。

## 版本来源与表示

[`pyproject.toml`](../../pyproject.toml) 的 `version` 是 QuickQuip 项目版本号的唯一来源；前端应用展示使用该来源。`frontend/package.json` 的包版本独立维护，不随项目发版同步。

| 阶段 | 项目版本示例 | 含义 |
|---|---|---|
| 开发起点 | `1.15.1-dev.0` | 开始准备目标版本 1.15.1。 |
| 开发检查点 | `1.15.1-dev.1` | 同一目标下的新一批开发成果。 |
| 发布候选（可选） | `1.15.1-rc.1` | 范围冻结，进入发布验收。 |
| 正式发布 | `1.15.1` | 已接受的正式发行版本。 |
| 下一主题开发 | `1.16.0-dev.0` | 开始准备新的主题更新。 |

项目版本字符串不带 `v` 前缀；发行 tag 带 `v`，例如 `v1.15.1`、`v1.15.1-rc.1`。Python 打包工具可能将上述开发与候选写法规范化为 `1.15.1.dev1`、`1.15.1rc1`；核对发行元数据时按等价版本识别。

## dev 分支

### 目标版本

dev 使用 `<目标正式版本>-dev.N`，例如 `1.15.1-dev.0` 或 `1.16.0-dev.0`。目标表达下一次计划发布的版本，允许随范围调整。

正式发布并回灌后，默认进入当前 Minor 的下一个 Patch 开发起点，例如 `1.15.0` 发布后进入 `1.15.1-dev.0`。确定开启新主题时，再进入下一个 Minor，例如 `1.16.0-dev.0`。维护者也可以按已确定的发布计划选择其他目标。

重新确定目标版本时，开发批次号从零开始。此类调整只修改未发布的开发目标；已发布 tag 和发行物保持原样。

### 开发批次

`N` 是从零开始、人工维护的开发批次号。同一目标版本内，在阶段性集成、测试部署或交接时按需递增；日常 Commit 和 PR 无需逐次更新。它独立于 Git 的提交数和合并提交数，也不作为构建的唯一标识。

需要精确复现代码时，同时记录 Git SHA；工作区存在未提交改动时，应明确记录该状态。仅凭相同的 `dev.N` 无法确认代码完全一致。

版本更新可作为 `chore:` 改动按 Develop direct 流程处理。Commit、push 和其他发布操作仍遵守 [`branching.md`](branching.md) 的授权规则。

## 发布候选与正式冻结

发布时确定目标 `X.Y.Z`、发行范围和候选 SHA。需要预发布验收时，使用 `X.Y.Z-rc.1`，后续候选依次递增；也可以直接准备正式版本。

RC 的同一目标下以验收修复为主；范围发生实质变化时重新评估目标与验收范围。发行流水线从 CHANGELOG 的基础版本段 `X.Y.Z` 提取 RC 的发布说明。正式发布前更新日期、升级说明与最终内容，将项目版本定为 `X.Y.Z`，按发布流程在已接受提交上打 tag。

已发布的 RC 和正式 tag 均保留原样；发布新候选使用新编号。公开预发布产物的版本变化需考虑已有版本排序和使用者，目标调整规则不用于覆盖既有发行物。

## 回灌与 Hotfix

发布回灌后检查 dev 的目标版本：完成当前目标的常规发布，按计划设置下一开发起点；通过 `release/*` 收束期间已启动的后续开发，继续保持其有效目标。

Hotfix 使用正式版本序列中可用的下一个 Patch。回灌时保留 dev 正在推进的目标及批次；若该目标已被 hotfix 发布占用，则选择新的未发布目标，并从 `dev.0` 开始。

| 场景 | 回灌后的 dev 版本 |
|---|---|
| dev 为 `1.16.0-dev.3`，main 发布 `1.15.1` hotfix | 保持 `1.16.0-dev.3`。 |
| dev 为 `1.15.1-dev.3`，main 发布 `1.15.1` hotfix | 通常调整为 `1.15.2-dev.0`。 |
| dev 完成 `1.15.1` 正式发布，继续当前主题 | 通常进入 `1.15.2-dev.0`。 |

版本字段的合并冲突按当前发布计划处理。核对回灌结果时，同时确认修复已进入 dev，且项目版本仍表达其下一次计划发布的目标。
