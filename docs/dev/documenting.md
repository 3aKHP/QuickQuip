# QuickQuip 公开文档规范

本文件是 QuickQuip 的“文档的文档”，定义全仓公开文档的写作、维护和审查要求。所有人类贡献者与 AI 协作者撰写、修改、生成或审查公开文档时，均须遵循本规范。

适用内容包括根目录项目文档、`docs/`、生产模板的使用说明、公开协作指令、Issue／PR 模板、随包 Skill 文档与生成副本。配置示例中的解释文字和面向使用者的脚本说明同样适用。

文档的质量目标是让目标读者理解事实、做出决定并完成操作。内容取舍、结构和验证都围绕这个目标展开。

## 文档职责与权威来源

每份文档应有明确读者、主要任务和事实来源。按以下职责组织内容：

| 文档位置 | 主要职责 |
|---|---|
| 根目录 `README.md` | 项目入口、功能概览、快速开始与导航 |
| `docs/glossary.md` | 项目概念的统一名称、简短定义和详细契约入口 |
| `docs/user/` | 群友能使用的功能、命令、预期结果与常见问题 |
| `docs/admin/` | 安装、配置、升级、运维、备份恢复与排障 |
| `docs/dev/` | 开发契约、实现原理、工程规范与交付流程 |
| `docs/dev/adr/` | 重要技术选择的背景、理由、影响和决策历史 |
| `CHANGELOG.md` | 各版本用户可感知的变化及升级事项 |
| `ROADMAP.md` | 已确定方向、待调研问题与候选计划 |
| 公开模板与示例目录 | 随模板使用的前提、字段说明和操作指引 |

同一事实由最贴近其读者与职责的一份文档维护，其他页面链接到该权威来源。开发原理、管理员操作和用户体验可以分别说明各自所需的信息；易变字段表、维护 SQL 和长命令清单统一维护。

新建独立文件须有稳定且独立的职责。新增页面在 [`../index.md`](../index.md) 与所属目录索引登记；调整标题、文件名或位置时同步维护链接和锚点。

同系列 ADR 在[决策索引](adr/README.md)集中登记各篇与模板，总导航登记系列入口。

## 读者与内容组织

- 开篇说明文档解决什么问题、适合谁阅读；需要权限、版本或部署形态时，给出具体前提。
- 先提供结论、用法或操作入口，再解释读者需要的原因和机制。标题围绕任务命名。
- 用户文档使用熟悉的词语与具体例子。管理员文档交代执行位置、配置来源和生效方式。开发文档解释契约与实现依据。
- 一段发展一个主要意思，句子按因果或操作顺序衔接。平行信息用列表，映射和比较用表格，操作步骤用有序列表。
- 篇幅由任务复杂度决定。删除空泛开场、重复总结、同义堆叠和与当前任务无关的实现细节。
- 教程、项目介绍和彩蛋文档可按自身定位使用亲切或幽默的语气；事实、命令和操作条件保持准确。

## 当前事实、计划与证据

现行说明直接描述目标版本的完整行为。演变过程、代际差异和事故经过放在 CHANGELOG、迁移说明或明确标识的历史材料中。正文保持连贯成文，避免“原先……现在……”或“不是……而是……”式修补痕迹。

- 项目行为以实际实现、字段校验、公开模板和既定契约为依据。核对保存、发布、加载、执行与失败发生的阶段。
- 命令名、参数、配置键、默认值、页面导航和错误名称采用实际拼写。涉及全局、渠道、模型、群或私聊时写明作用范围。
- 已实现能力写入现行说明；候选设计与调研事项进入 ROADMAP，并给出当前需要解决的问题。已完成的计划同步更新状态。
- 外部服务、依赖或平台信息注明适用版本；易变信息给出核对日期和直接支持结论的官方来源。来源不足的判断写明推断依据，待确认的事实先核实再写成确定结论。
- 验证记录写清对象、版本／提交、方法和结果。使用与实际证据相符的动词，例如“语法校验通过”“隔离数据库执行通过”“Windows 实机启动通过”。

## 术语与架构决策

跨文档使用的项目概念在[术语表](../glossary.md)统一名称、别名和简短定义。参数约束、易变清单和操作步骤由领域文档维护，术语条目链接到相应契约。引入或调整概念时，在同一变更核对术语条目及使用位置。

影响结构、状态所有权、持久化、协议兼容或后续开发约束的重要决定，按[ADR 规则](adr/README.md)保留背景与取舍。ADR 可以围绕选择比较有证据的候选方案，记录当时收益与代价；当前行为和操作继续由现行契约说明。历史补录注明记录日期、可核实的原始决策日期及公开依据，内部来源映射留在内部工作区。

ADR 状态表达决定是否获接受及是否被替代，实现进度由关联变更跟踪。文稿审阅进度放在交付或评审记录中。发布新决定或改变旧记录状态时，同步维护决策索引、替代链接和 self-docs 副本。

## 文风：面向读者的确定表达

优先写清主体、动作、条件和结果，使用具体、直接的陈述。每句限制或保留都应能回答：**它帮助读者做出什么决定，或执行什么操作？**

### 模型协作者重点自查

本节的文风分析重点面向 GPT 系模型及其他可能运行在 Codex 中的模型；其他模型同样应据此自查，有则改之，无则加勉。所有贡献者都按本节要求审查自己的文字。

“人类可读性差”涵盖读者适配、词句表达、逻辑连接和信息取舍等具体问题。本节结合写作与文档研究，将这些问题转化为项目审查要求；以目标读者能否理解事实并完成任务判断修订效果。

#### 预防性免责语调

**预防性免责语调**是围绕一个事实或成果，连续添加限缩、否定推论和待办边界，使作者的责任保护占据超过读者实际决策需要的篇幅。“免责声明”描述其表达形式，“过度边界”描述其组织信息的方式。

典型组织顺序为：陈述成果 → 限缩意义 → 列举无法推出的结论 → 补充尚待完成的事项。例如：

> 这只代表配置检查通过，不能认为部署成功，也不证明上游可用，真实渠道仍需验证。

这类写法容易预设读者会过度解读，把作者的责任保护放在信息表达之前，并反复制造“还有欠账”的感觉。具体操作限制与泛化保留混在一起，会削弱真正重要的条件。

审查时按以下特征定位问题：

| 特征 | 常见句式 | 修订方向 |
|---|---|---|
| 免责声明 | “这只代表……”“也不证明……” | 准确命名已完成的验证及结果 |
| 过度边界 | 连续罗列当前任务之外的场景、例外和验证 | 保留影响当前读者选择的条件，其他内容归入对应任务文档 |
| 欠账式收尾 | 段落反复以“仍需……”“尚待……”结束 | 待办集中记录为有具体问题和跟踪入口的计划 |
| 预设误解 | “不能认为……”“也不意味着……” | 直接说明当前行为、适用条件或下一步操作 |

修订应调整信息职责与结构，保持事实准确。单纯替换词语会保留原有的免责组织方式。以下例子展示面向读者的表达：

| 场景 | 写法 |
|---|---|
| 配置检查结果 | “配置校验通过。部署健康检查由部署脚本执行；渠道连通性在模型探测入口查看。” |
| 保存配置 | “保存会更新草稿。点击应用后，等待 Bot 加载状态显示目标版本。” |
| 功能启用条件 | “工具调用默认关闭。在工具与技能页面开启，保存草稿后应用。” |
| 后续产品计划 | “Web 已支持报告配置编辑。运行反馈改进记录在 ROADMAP 的报告配置体验条目。” |
| 明确失败条件 | “重复的 MCP ID 会使配置保存校验失败，请为每个服务设置唯一 ID。” |

“不”“也不”“仍”“仅”等词用于搜索候选句。审查依据是句子的职责、读者收益和出现密度；保留表达具体规则、现实状态与操作条件的必要否定。例如“重启不会应用草稿”直接解释生效方式，“删除前先迁移群绑定”直接指导操作。

#### 读者适配与实现细节

**读者适配失败**表现为文档直接复述作者理解实现的过程，读者需要自行从函数、对象和状态转换中提取用法。**实现细节侵入正文**表现为内部标识符或源码片段承担了本应由自然语言完成的解释。

- 先写读者需要理解的行为与完成的操作。管理员文档说明配置入口、作用范围和生效方式；开发文档按理解与维护契约的需要解释实现。
- 自然语言承担解释，标识符帮助准确定位对象。用户需要输入的命令、配置键、错误码和相关文件路径保留实际名称；内部函数名、类名和调用链按读者任务选择。
- 代码块须服务于明确任务，选取足够完成该任务的示例，并说明执行位置、替换项和预期结果。介绍功能时用文字解释行为；实现分析引用关键片段并解释其作用。
- 先选择必要的内容，再按代码格式规则排版。正文的条件、原因、先后关系和读者操作写成完整句子。

例如，管理员需要知道“保存会生成草稿，应用后等待机器人加载目标版本”。支撑这一行为的内部对象与方法由开发契约解释。Google 的[文档实践](https://abseil.io/resources/swe-book/html/ch10.html)按读者区分使用说明与实现细节，[代码字体规范](https://developers.google.com/style/code-in-text)说明准确标记代码实体的用途；[GPT-4 文档读者适配研究](https://link.springer.com/chapter/10.1007/978-3-031-72781-8_11)也观察到面向管理者调整内容后理解与可读性的改善。

#### 常见表达与内容失真

| 问题 | 审查时关注的表现 | 修订要求 |
|---|---|---|
| 名词化与抽象表达堆积 | 一句话塞入多层“管理／机制／状态／一致性”等抽象概念，主体和动作难以辨认 | 写清谁在什么条件下做什么，例如“确认机器人已加载刚发布的配置” |
| 华丽但空泛的评价 | “全面提升稳定性”“构建健壮闭环”等评价占据篇幅，实际变化模糊 | 写清改变后的行为、触发条件与读者收益，以具体事实支撑评价 |
| 机械的文章模板 | 小任务也重复预告、固定分节、阶段标记和总结；不同文档使用同一套话术 | 按任务需要组织结构，保留有导航或解释作用的段落 |
| 重复与低信息增量 | 开篇、正文、提示框和结尾反复表达同一事实 | 每段增加读者需要的信息，合并同义复述，其他入口链接到权威说明 |
| 排版替代论述 | 标题、加粗、列表或斜杠串起关键词，句子之间的关系靠读者拼接 | 写明条件、原因与操作顺序；列表承载真正平行或有序的信息 |
| 措辞流畅，关键条件缺失 | 功能概括完整，默认值、权限、前提、失败行为或生效阶段被省略 | 对照实际契约补齐影响读者决定与操作的条件 |
| 按熟悉模式补写行为 | 根据函数名、惯常设计或同类产品，补出貌似合理的功能说明 | 逐项依据实际实现、公开模板与既定契约写明行为 |
| 连续改写造成语义漂移 | 润色、压缩或重组时遗漏条件、改动事实、混淆状态或改变引用 | 对照原文与权威来源核对受影响内容；保留正确事实及其条件，同步关联说明与引用 |

这些审查项的研究依据包括：

- [语体研究：Do LLMs write like humans?](https://arxiv.org/html/2410.16107)：GPT-4o 与 Llama 3 的英语语料体现出名词偏重、固定词汇偏好及文体适配问题。
- [修辞研究：Prompt Sensitivity in AI Writing](https://onlinelibrary.wiley.com/doi/full/10.1111/modl.70089)：GPT 英语议论文中的目标宣告与阶段标记具有模板倾向，提示方式会影响修辞表现。
- [质量分类研究：Measuring AI “Slop” in Text](https://arxiv.org/html/2509.19163v1)：分别考察信息密度、相关性、重复、模板化、连贯性、冗长和词语复杂度，支持按具体问题审查文字。
- [代码文档研究：Using Large Language Models to Document Code](https://arxiv.org/html/2408.14007v1)：GPT-3.5 生成 Javadoc 的实际案例包含关键条件遗漏与行为误述。
- [文档编辑研究：LLMs Corrupt Your Documents When You Delegate](https://arxiv.org/html/2604.15597v1)：跨模型、跨领域的多轮编辑实验观察到内容损失与失真，全局重组任务更容易出现问题。

### 限制、警告与后续事项

- 把适用条件放在相关步骤前，把具体失败原因放在排障位置，把已知问题放在对应版本或功能说明中。
- 警告说明触发条件、具体后果与处理动作。数据删除、覆盖、费用、权限和兼容性问题要让读者在执行前看见。
- 验证覆盖与尚待确认的事项集中写在交付记录或专门的验证段落，注明具体对象及下一步；面向使用者的文档保留影响使用决策的事实。
- 同一限制在权威来源完整说明，其他入口用必要提示与链接引导。正文避免每段追加通用风险声明。
- 使用清楚、平实的措辞。避免营销式评价、虚构的复合术语、空泛的“值得注意”“重要的是”和结尾口号。

## 操作文档与排障

一个操作流程应能让目标读者从前提走到可观察的结果：

1. 给出所需权限、运行状态、工具和输入，以及执行目录、Shell 或界面入口。
2. 按真实依赖顺序组织步骤。新安装从目录或文件创建开始；迁移涉及初始化时，安排可实际访问的入口。
3. 写明操作修改的对象、保存位置及生效方式，区分保存草稿、应用、重新加载与重启。
4. 给出成功时可观察的输出或状态，并说明有代表性的失败原因与处理动作。
5. 涉及数据维护或不可逆操作时，说明停服与备份条件、实际目标、改变和保留的数据、恢复入口。

平台与部署形态的差异就近说明。Windows、源码安装和容器示例使用各自实际可用的路径和工具。Shell、容器工作目录和主机文件路径标识清楚。

排障按“现象 → 原因／检查方法 → 处理动作”组织。页面错误、配置校验失败、运行时装载失败和远端调用失败分别解释。执行会产生真实请求或费用时，在操作入口说明。

## 配置、命令与示例

- 示例符合当前解析器、字段层级、类型、引用约束与默认策略。解释继承值、空值、关闭值和零值的具体语义。
- 完整配置、结构片段和伪代码明确标识。片段说明合入位置及需要保留的配置；占位符说明替换方式。
- 命令应可复制执行，代码块内放可用语法。交互提示符、预期输出和解释文字单独呈现；示例内注释须符合对应语言。
- SQL、删除与覆盖命令标明目标和前提。验证有副作用的示例时使用隔离环境或合成数据，检查需要保留的数据。
- 默认值和长字段表在权威来源维护；其他文档用链接和与当前任务直接相关的小例子说明。
- 新增示例优先使用现有解析器、校验器或工具验证。语法、引用、执行结果和平台可用性按实际完成的验证分别记录。

## 格式、术语与公开信息

- 文本统一使用 UTF-8 与 LF。Markdown 段落和列表项保持自然换行；按结构或语义需要换行。
- 中文散文使用弯引号“”与‘’。代码、命令和配置采用语法所需的 ASCII 引号，保证复制执行。
- 配置键、命令、文件路径、错误码与标识符用行内代码。标题按层级组织，表格用于容易对照的信息，代码块注明语言。
- 同一概念使用一致术语。首次出现的缩写在需要时解释，界面标签采用实际名称；代码标识符保持原样。
- 仓库文件使用相对链接，外部引用链接到直接支持事实的页面。图片与图表提供说明；图示、截图与界面变更同步维护。
- 公开内容使用可分发的路径、模板与合成标识。真实账号、群号、token、登录态、本机绝对路径和私有拓扑留在受控环境。
- 工作草稿与执行记录归入本地私有工作区。公共说明通过仓库分发内容即可理解，生产运维示例来自 `prod.example/`，应用凭据来源按项目约定使用根目录 `.env`。

## 维护与审查

行为、配置、协议、命令、版本或路径发生变化时，在同一变更中更新拥有该事实的文档、例子、相关入口与生成副本。历史材料保留当时事实并注明历史用途，当前使用入口指向现行说明。

修改 self-docs 同步源后，运行仓库提供的生成工具，并将权威文档和副本放在同一变更中：

```bash
python scripts/ci/sync_self_docs_references.py
python scripts/ci/sync_self_docs_references.py --check
```

同步源的权威名单见 [`../../scripts/ci/sync_self_docs_references.py`](../../scripts/ci/sync_self_docs_references.py)。生成副本通过工具维护。

文档交付前检查：

- 目标读者能否找到入口、理解条件并完成任务？
- 当前行为、计划和历史事实是否各归其位，权威来源是否明确？
- 字段、默认值、命令、权限、页面名称及生效顺序是否与实际行为一致？
- 示例是否经过适当验证，链接、锚点、编码和生成副本是否一致？
- 文风是否适合读者，解释是否清楚，是否出现实现细节侵入、抽象堆叠、重复、模板化或排版替代论述？限制和警告是否有具体用途，是否出现预防性免责、过度边界或修补痕迹？
- 改写是否保留了正确事实、关键条件与生效阶段，关联引用是否同步？
- 公开内容是否符合路径、凭据与隐私要求？

评审指出具体段落、读者会遇到的问题及修订办法。关键词搜索用于定位候选，句子功能与事实依据决定结论。验证和评审安排遵循 [`branching.md`](branching.md)，代码与测试规范分别见 [`style.md`](style.md) 和 [`testing.md`](testing.md)。
